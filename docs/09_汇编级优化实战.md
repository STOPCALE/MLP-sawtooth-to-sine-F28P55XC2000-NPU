## 1. 方法论：这轮唯一没失手的东西

四条纪律（沉淀自 `06`/`08` 的教训）：

1. **别猜，看汇编。** 每个改动先离线跑 `cl2000 -O2 ... -k hand_infer.c` 生成 `.asm`，
   在**纸上预演**完再上板。C2 的三稿迭代 = 3 次编译 ≈ 30 秒，**零烧写**。
2. **一次一个变量 + 常数回归判据。** 判据 = CH22 必须仍 ≈0.0314；
   它由解析真值 $y=-\sin(\pi s)$ 生成，比任何 golden 对拍都便宜、且更"硬"。
3. **PC 先预演。** gcc 编译同一个 `hand_infer.c`，数值不动才轮到板子。
4. **直读测量。** `read_vofa.py` 拉数据（免手抄）；每轮记录"耗时 + 周期/MAC + 比值"。

## 2. C1：一行类型改动 = 1.54×

### 2.1 改动

```c
int32_t o, i;   →   int16_t o, i;      /* 累加器 acc 仍是 int32_t, 不动 */
```

### 2.2 为什么敢改：范围证明

循环下标最大值 = `63*64 + 63 = 4095` ≪ 32767，16 位绰绰有余。

### 2.3 编译器给的"隐藏奖励"：RPTB 硬件循环

**改前**（10 条/迭代，其中 4 条是软件循环控制）：

```asm
||$C$L2||:
        MOV       ACC,*XAR5++    ; 读 x[i]
        MOVX      TL,*XAR1++     ; 读 W_q[o][i]
        SUBB      XAR7,#1        ; ← 循环计数（32位）
        SUBL      ACC,XAR0       ; x[i]-z_in
        IMPYL     ACC,XT,ACC     ; 32×32 乘法
        ADDL      P,ACC          ; acc +=
        MOVB      ACC,#0         ; ← \
        SUBB      ACC,#1         ; ←  | 每轮凭空造一个 32 位 -1 来比较
        CMPL      ACC,XAR7       ; ←  |
        B         ||$C$L2||,NEQ  ; ← / 分支（每次迭代都有流水线惩罚）
```

**改后**（6 条/迭代，0 条循环控制）：

```asm
        RPTB      ||$C$L3||,AR6  ; ← 硬件块循环：重复 N 次、零分支
||$C$L2||:
        MOV       ACC,*XAR0++    ; 读 x[i]
        MOVX      TL,*XAR7++     ; 读 W_q
        SUBL      ACC,XAR1       ; x[i]-z_in
        IMPYL     ACC,XT,ACC     ; （还是 32×32 → 留给 C2）
        ADDL      P,ACC          ; acc +=
        NOP
```

**关键认知**：这不是"少 4 条指令"的线性收益。`int32_t` 下标让编译器**放弃**了硬件循环
（32 位计数器放不进 16 位的 AR 寄存器，只能"4 条控制 + 取分支"软件循环）；
`int16_t` 下标（C28x 的原生宽度、直接躺在 AR 里）让编译器**换了一种循环实现**。

### 2.4 数据

| 指标 | v0 | C1 | 变化 |
|---|---|---|---|
| CPU 10 点耗时 | 6727.5 µs | 4374.6 µs | **1.54×** |
| 周期/MAC | 23.9 | 15.5 | −35% |
| 比值 | 12.01× | 7.82× | — |
| CH22 | 0.0314 | 0.0314 | ✅ |

### 2.5 为什么不是 1.67×（10→6 的比例）？

剩下的 ~9.5 周期/MAC 是**停顿**，不是指令条数：32 位 `IMP YL` 的延迟、双数据读口、
流水线气泡。→ 这是 C2 的假说来源。

## 3. C2：从 6 条到 1 条 —— 一条指令的循环

### 3.1 假说

`IMP YL` 是 32×32 乘法，但两个乘数实际只占 16 位
（`x[i]-z_in ∈ [0,255]`，`W_q ∈ [-128,127]`）。改成 16×16 应能命中更快的乘法路径。

### 3.2 第一稿：直接改（离线否掉）

```c
int16_t xs = (int16_t)(x[i] - (int16_t)L->z_in);
acc += (int32_t)(xs * L->W_q[o * L->in_dim + i]);
```

编译结果（**9 条/迭代，比 C1 的 6 条还长**）：

```asm
        RPTB      ||$C$L3||,AR7
||$C$L2||:
        MOV       AL,AR3            ; ← z_in 低位每轮重搬
        MOV       T,*XAR0++         ; x[i]
        SUB       T,AL              ; T = x[i]-z_in
        MOVL      ACC,*-SP[6]       ; ← 可疑的 32 位存取对
        MPYA      P,T,*XAR6++       ; P += T × w[i]   ← 单周期 MAC 出来了!
        MOVL      *-SP[6],ACC       ; ←
        NOP
        NOP
        NOP
```

好消息：`MPYA`（乘加进 P）说明编译器"看懂"了意图；
坏消息：外围全是噪声。**在纸上就枪毙了**，没烧一次板。

### 3.3 第二稿：把 z_in 提到局部变量（还是 9 条）

```c
const int16_t z16 = (int16_t)L->z_in;      /* 内层只写 x[i]-z16 */
```

汇编几乎不变（`MOV AL,*-SP[2]` 代替 `MOV AL,AR3`，存取对和 NOP 依旧）。

**推论**：编译器的痛点不是 z_in 放在哪，而是"**每轮都要现算 `x−z` 再乘**"。

### 3.4 第三稿：把零点半减**提出**内层（成功）

`x[i]-z_in` 只依赖 i（层内不变式），却被每个输出行**重算 64 遍**。
把它提出来先算进 `xs_buf`（64 个 int16，共 128 B）：

```c
static int16_t xs_buf[64];
for (i = 0; i < L->in_dim; i++)
    xs_buf[i] = (int16_t)(x[i] - (int16_t)L->z_in);
for (o = 0; o < L->out_dim; o++)
{
    int32_t acc = L->b_int[o];
    for (i = 0; i < L->in_dim; i++)
        acc += (int32_t)(xs_buf[i] * L->W_q[o * L->in_dim + i]);
    ...
}
```

编译器给出的答案 —— **一个"一条指令"的循环**：

```asm
        MOV   P,#0                       ; P = 0（MAC 累加器）
        MOVL  XAR0,#xs_buf
        RPT   AR5                        ; 单指令硬件重复 64 次（重复期间零取指）
||      MAC   P,*XAR0++,*XAR7++          ; 循环体就这 1 条（"||" 是 RPT 的重复标记）
        ADDL  ACC,P                      ; acc = b_int[o] + P（循环外，每行一次）
```

**一条 `MAC` 指令里发生的四件事**（DSP 的看家本领）：

1. 从 `xs_buf` 读一个 16 位（XAR0 后自增）
2. 从 `W_q` 读一个 16 位（XAR7 后自增）
3. 16×16 → 32 位精确乘法
4. 累加进 32 位 P

**`RPT` vs `RPTB`**：`RPTB` 重复的是一个**块**；`RPT` 重复的是**下一条指令**，
重复期间该指令锁在取指缓冲里 —— 对单指令循环体：零取指、零分支、零控制开销。

### 3.5 范围证明（16 位通路的正确性依据）

```
xs = x[i]-z_in  ∈ [-128, 255]      （x ∈ [-128,127]，z_in ∈ {0,-128}）
w  = W_q[..]    ∈ [-128, 127]
乘积            ∈ [-32640, 32385]  ⊂ int16 → C 语言层 16 位乘法无损
```

（`MAC` 指令内部本就是 32 位精确累加；这个证明是为了 C 语言层 `xs*w` 的语义安全。
**已写进 `hand_infer.c` 注释 —— 换模型/换量化参数必须重新验算。**）

### 3.6 数据

| 指标 | v0 | C1 | C2 | 变化（vs C1） |
|---|---|---|---|---|
| CPU 10 点耗时 | 6727.5 | 4374.6 | **2326.7 µs** | **1.88×** |
| 周期/MAC | 23.9 | 15.5 | **8.3** | — |
| 比值 | 12.01× | 7.82× | **4.03×** | — |
| CH22 | 0.0314 | 0.0314 | 0.0314 | ✅ |

### 3.7 教训

- **编译器不魔法，它在等你写出"它认识的样子"**——它认识的样子 = 纯双流 MAC 循环。
- **循环不变式的威力**：一次 64 次的小预处理，把 4096 次乘法的内层体从 6 条压到 1 条。
- **离线汇编迭代 = 拿 10 秒换一次烧写**：C2 三稿成本 ≈ 30 秒编译 + 0 次上板。

## 4. C3：把 W_q 搬进 RAM（1.57×）

### 4.1 假说（来自 C2 的余量分析）

MAC 每个周期都要读一个权重；权重在 FLASH 里，数据读的等待周期会给**每一个 MAC** 收税。
可证伪的判据：**把权重搬进 RAM，看 CH21 动不动。**

### 4.2 改动：去掉 `const` + 指定 RAM 段（不用改链接脚本）

```c
#if defined(__TI_COMPILER_VERSION__)   /* gcc 不认识这个 pragma, PC 侧屏蔽 */
#pragma DATA_SECTION(L1_W, "ramgs1")   /* 8192B 恰好装满 RAMGS1 */
#endif
static int16_t L1_W[4096] = { ... };   /* ← 去掉 const */
```

机制（一条链子，缺一不可）：

1. **去掉 `const`** → 数组从"只读、焊在 FLASH"变成"已初始化的读写变量"
2. **`#pragma DATA_SECTION` 指向 `ramgs1`/`ramgs2`** —— 链接脚本里**已有现成空段**
   （RAMGS1/GS2 各 8KB；GS0-2 空闲；**GS3 被 NPU 的 `.bss.noinit.tvm` 占用，不能碰**）
3. **`.cinit` 自动初始化**：开机时 C 运行时把初始值从 FLASH 镜像拷进 RAM
   （与 `.data` 段同一套机制，`--rom_model` 的标准流程）

### 4.3 验证落点（不能假设，要看 map）

```
ramgs1: load addr=00082988, load size=00001004 bytes, run addr=0000e000, run size=00001000 bytes
ramgs2: load addr=0008398c, load size=00000059 bytes, run addr=00010000, run size=00000080 bytes
```

- `ramgs1` **run 地址 0xE000 = RAMGS1**（8192 B = L1_W 精确装满）
- load 镜像留在 FLASH（0x82988），由 `.cinit` 开机拷贝
- RAMGS3（NPU）原封未动 ✅

### 4.4 数据

| 指标 | v0 | C1 | C2 | **C3** | 变化（vs C2） |
|---|---|---|---|---|---|
| CPU 10 点耗时 | 6727.5 | 4374.6 | 2326.7 | **1481.9 µs** | **1.57×** |
| 周期/MAC | 23.9 | 15.5 | 8.3 | **5.3** | — |
| 比值 | 12.01× | 7.82× | 4.03× | **2.57×** | — |
| CH22 | 0.0314 | 0.0314 | 0.0314 | 0.0314 | ✅ |

**累计（v0 → C3）= 4.54×**（比值 12.0× → 2.6×）。

### 4.5 教训

- **"搬 RAM"不是玄学**：FLASH 数据读等待在**每个 MAC** 上收税，积少成多。
- **不必动链接脚本**：`ramgs1/ramgs2` 这类"现成空段"是链接脚本送你的礼物。
- **生成物防线**：手动改完还要**同步生成器**（`export_c_header.py`），
  并重跑对拍——本次重生成其余三个文件**零漂移**，MCU 头只剩预期改动 → 才算真正归档。
