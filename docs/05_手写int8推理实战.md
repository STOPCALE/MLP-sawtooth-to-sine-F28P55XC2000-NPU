## 1. 数字地基：从哪读、读到什么

### 1.1 为什么选 QDQ ONNX，而不是 fbgemm 的 `.pt`

| | `saw2sin_qat_state.pt` | `saw2sin_int8.onnx` ← **选它** |
|---|---|---|
| 来源 | QAT（PyTorch fbgemm 后端） | PTQ（onnxruntime QDQ 格式） |
| 激活类型 | **quint8 无符号**（[0,255]） | **int8 有符号**（[−128,127]） |
| 零点风格 | 输入 127 / 隐藏 0 / 输出 128 | 输入 0 / 隐藏 −128 / 输出 0 |
| bias | **float32**（需自己吸进整数域） | **int32**（量化器已吸收） |
| 权重存放 | 藏在 `_packed_params` 的 tuple 里 | 独立 initializer，命名清晰 |
| 读数难度 | 高（要 `.int_repr()` / `q_per_channel_scales()`） | 低 |

**教训**：两种格式的 `scale/zero_point` 是**绑定的**，只能照**一套**数字写，并和**那一套**对拍，不能混用。

### 1.2 量化站点表（QDQ ONNX）

| 站点 | initializer 名字 | 值 |
|---|---|---|
| 输入 `s` | `s_scale` / `s_zero_point` | 0.0078431 / 0 |
| 第 1 层权重 | `net.0.weight_quantized` (64,1) int8 | per-channel scale × 64 |
| 第 1 层 bias | `net.0.bias_quantized` (64,) **int32** | 已吸收 |
| 第 1 层输出 | `/net/net.1/Relu_output_0_scale` / `_zero_point` | 0.0062498 / **−128** |
| 第 2 层 | `net.2.*` | (64,64) |
| 第 2 层输出 | `/net/net.3/Relu_output_0_scale` / `_zero_point` | 0.0089614 / **−128** |
| 第 3 层 | `net.4.*` | (1,64) |
| 输出 `y` | `y_scale` / `y_zero_point` | 0.0078392 / 0 |

> ⚠️ 图里**只有 3 个 Linear + 2 个 ReLU**（`net.0/2/4` 是 Linear，`net.1/3` 是 ReLU）。
> **最后一层没有 ReLU**，它的输出直接就是 `y`——不存在 `net.5`。

### 1.3 一个必须建立的直觉：zero_point 反映"数据形状"

| zp 值 | 含义 | 本模型出现在 |
|---|---|---|
| 0 + 有符号 | 数据关于 0 对称 | 输入 `s ∈ [−1,1]`、输出 `y ∈ [−1,1]` |
| −128 | 数据**非负** | ReLU 输出 `[0, max]` |

**看到 zp 就能反推出这层数据长什么样**——这是量化工程师的基本直觉。

### 1.4 尺子是在哪一步"诞生"的？

| 阶段 | 脚本 | 产物 | 有 scale 吗 |
|---|---|---|---|
| 训练 | `saw2sin_mlp.py` | `saw2sin_model.pt` | ❌ 只有 float 权重 |
| 导出 | `onnx_export.py` | `saw2sin.onnx` | ❌ |
| **量化** | `onnx_int8_quant.py` | `saw2sin_int8.onnx` | ✅ **尺子在这里诞生** |
| 推理 | onnxruntime | — | 只读，不算 |

量化器内部做的事：标定 4096 个点 → 统计每层激活 min/max → 算 scale/zp →
权重按通道算 scale → bias 算成 int32 并吸收 → **全部写成 initializer 存进文件**。
推理时只是**读常量**。

## 2. 完整公式（带 zero_point 的通用形式）

对一层（输入维度 $in$，输出维度 $out$）：

$$\text{acc}[c]=\sum_{j=1}^{in}\big(W_q[c,j]-z_w\big)\Big(q_{in}[j]-z_{in}\Big)+b_{int}[c]$$

$$q_{out}[c]=\mathrm{clamp}\Big(\mathrm{round}\big(\text{acc}[c]\cdot M[c]\big)+z_{out},\ -128,\ 127\Big)$$

$$M[c]=\frac{S_{in}\cdot S_w[c]}{S_{out}},\qquad \hat x[c]=S_{out}\big(q_{out}[c]-z_{out}\big)$$

### 关键认识

1. **`M` 必然是正数**（三个正尺子的比值）→ **算出负 M 就是参数传错了**，这是最强自查信号。
2. **ReLU 不需要单独一行**：隐藏层 $z_{out}=-128$ 正好代表实数 0，所以 `clamp` 的下界**天然实现 ReLU**。
3. **`b_int` 已吸进整数域**：ONNX QDQ 的 `bias_quantized` 就是 int32，且恒满足
   $$S_{b}=S_{in}\cdot S_w\quad\Longleftrightarrow\quad b_{int}=\mathrm{round}\!\Big(\frac{b}{S_{in}S_w}\Big)$$
   （已用 `net.0/net.2/net.4` 三层逐一验证成立）
4. **每层输出尺子 = 下一层输入尺子**（`S_out(k) = S_in(k+1)`）——串联时唯一要记住的东西。
5. **入口只量化一次、出口只反量化一次**，层与层之间流的是**整数**。

## 3. 验算链（`s = 0.5` 全程记录）

| 步骤 | 表达式 | 结果 |
|---|---|---|
| 入口量化 | `round(0.5 / 0.0078431)` | `q0 = 64` |
| 第 1 层累加 | `W_q0 @ q0 + b_int0`（int32） | `acc[0] = 404681` |
| 第 1 层 M | `S_in·S_w0[0]/S_out0` | `M[0] = 2.0359e-4` |
| 第 1 层输出 | `clip(round(404681·M[0]) − 128)` | `q1[0] = -46` |
| 反量化 | `0.0062498·(-46+128)` | `h1[0] = 0.51248237` |
| 第 2 层 M | `S_in2·S_w2[0]/S_out2` | `M2[0] = 2.3163e-3` |
| 第 3 层输出 | — | `q3 = -126` |
| 出口反量化 | `0.0078392·(-126 − 0)` | `y = -0.98774355` ✅ |

## 4. 六个坑（实战踩坑清单）

| # | 症状 | 原因 | 教训 |
|---|---|---|---|
| 1 | 结果全是 `.75` 之类的非整数 | `q_in` 忘 `round`，浮点混进了整数链路 | 整数链路的**每一步**都必须是整数 |
| 2 | `astype` 报错 / 数值溢出 | int8 直接累加会**溢出**（`127×64=8128 > 127`） | 累加器必须升 **int32** |
| 3 | 隐藏层整层全错 | 以为"不用减 zp 是因为第 0 层" | 真正原因是 **zp=0**；隐藏层 zp=−128，**必须减**（写成 `+128`） |
| 4 | 大量 127 / 同一个最大值反复出现 | 8 个位置参数传反（`S_in3` 与 `z_in3` 对调） | **scale 恒正**；建议用**关键字参数**调用 |
| 5 | `KeyError: /net/net.5/...` | 以为有第 3 个 ReLU | 图里只有 3 Linear + 2 ReLU，**最后一层输出即 `y`** |
| 6 | 注释写 −128、值是 0 | 注释与代码不一致 | 注释骗人 = 埋雷，**发现不一致立刻改** |

## 5. 对拍方法（验证才是一切）

### 5.1 让 onnxruntime 吐出中间张量（"开后门"）

ORT 默认只允许取 `graph.output`。要取中间激活，把目标张量**追加到 graph.output**：

```python
import onnx, onnxruntime as ort

m2 = onnx.load("saw2sin_int8.onnx")
vi = onnx.helper.ValueInfoProto()
vi.name = "/net/net.1/Relu_output_0_QuantizeLinear_Output"   # 想要哪个中间张量就写哪个
m2.graph.output.append(vi)

sess = ort.InferenceSession(m2.SerializeToString(), providers=["CPUExecutionProvider"])
h1_q = sess.run([vi.name], {"s": np.array([[0.5]], dtype=np.float32)})[0]
```

### 5.2 判据

| 对比对象 | 应达到 | 实测 |
|---|---|---|
| int8 中间张量 | **max diff = 0**（逐位） | 0 ✅ |
| float 输出 `y` | ≤ 1e-7（float32 舍入） | 1e-8 ✅ |

### 5.3 批量对拍结果（2026-10-07，1000 点）

| 对比对象 | 判据 | 实测 |
|---|---|---|
| 第 1 层 int8 中间张量 `q1` | 逐位相同 | **max diff = 0**（1000×64 = **64000 个整数全同**） |
| 输出 `y` | ≤ 1e-7 | **2.98e-8** |

> 单点对上有可能是巧合；**64000 个整数同时对上不可能是巧合**——这轮把实现钉死了。

**量化代价（全量 1000 点，`batch_bench.py` 实测）**：

| 模型 | vs 解析目标 max | mean |
|---|---|---|
| float | 4.582e-3 | 7.288e-4 |
| int8（PTQ） | 3.136e-2 | 6.942e-3 |

> 误差放大约 **6.8×**，与 `02_知识要点` §8.2 的既有记录一致。

**踩坑记录（批量化特有）**：把单点变量 `q0` 误传给批量链路 → numpy **静默广播**（`(1,)` 对 `(1000,1)`）→ 输出“max diff = 1.9833”。
诊断靠 **数值自洽推理**：`1.9833 = 0.99558（ORT 批量最大值）+ 0.98774（单点 y）`——两个数根本不同源。
**教训：批量推理的第一道验证永远是打印形状**（`(N,1)→(N,64)→(N,64)→(N,1)`）。

## 6. 自查清单 / 调试心法

**这三条不用跑代码，先心算就能挡掉大部分错误：**

1. **`scale` 与 `M` 恒为正** —— 出现负数 ⇒ 参数错
2. **饱和指纹**：某个**最大值反复出现**（如 `h2` 里一堆 `2.28516318 = 0.0089614×255`）
   ⇒ 值被 `clamp` 削平 ⇒ 查 scale 是否配错
3. **数值自洽推理**：若 `h3 = 0` 但 `q3 = −128`，由 $\hat x = S_{out}(q-z_{out})$ 立刻反推
   "实际传进来的 $z_{out}$ 是 −128" —— 板端没有打印时，**这是唯一可用的手段**。

## 7. 与部署（C 版 / 板端）的衔接

手写 Python 版把"数字链路"跑通了，**接下来 C 版要把同样的数字搬到 MCU**。可复用要点：

- **导出成 C 数组的内容**（每层）：`W_q`（int8）、`S_w`（per-channel）、`b_int`（int32）、
  `S_in/z_in/S_out/z_out`、以及预计算的 `M`
- **`M` 的处理**：PC 上先用 float 乘子跑通逻辑；纯整数硬件再改成 **定点** `M ≈ M₀·2^(−shift)`（int32 乘子 + 右移），
  这就是 TFLite/gemmlowp 的 `quantized multiplier`
- **可选优化**：把 $z_{in}$ 的贡献折叠进 bias：$\sum W_q(q_{in}-z_{in}) = \sum W_q q_{in} - z_{in}\sum W_q$，
  后项是**加载时算一次的 per-channel 常数** → 推理内循环少一次向量运算
  （推广：BN 折叠、常量折叠、零点折叠都是同一套路——**把"每个样本都要做的事"变成"一辈子只做一次的事"**）
- **接口设计建议**：把每层的 6 个量化参数打包成结构体（`LayerQuantParams`），
  避免 8 个位置参数裸传（见坑 #4）

## 8. 复述记录（2026-10-07，已闭环 ✅）

> 方式：合上资料，用户用自己的话回答；AI 批改。**第一轮 5 题偏差较大，第二轮全部通过。**

### 8.1 五题与批改结论

| # | 问题 | 通过要点 |
|---|---|---|
| 1 | float `s` → float `y` 经历哪些类型转换 | 入口量化 1 次、出口反量化 1 次；**层内每层各一次** `int8×int8 → int32 → ×M → round → int8` 往返；全链路**唯一的浮点乘法是 ×M** |
| 2 | `M` 里三个 scale 的含义 + 为何恒正 | 分别是输入激活 / 权重 / 输出激活的尺子；三者都是"一个量化单位代表多少实数"的**长度**，恒正 → 比值恒正 |
| 3 | `z_in` 的两个出现位置 | ① 显式：`acc = W_q @ (q_in − z_in) + b_int`；② 隐藏：展开后的 `−z_in·Σ_j W_q`（**权重行和**项），可**折叠进 `b_int`** |
| 4 | ReLU 在哪一行 + 为何不用 `max(0,x)` | 在 `np.clip(...)` 的**下界 −128**；因为隐藏层 `z_out = −128` 代表实数 0，**钳位下界与 ReLU 零点重合** |
| 5 | 输出层与隐藏层差在哪 | **只有 `z_out` 取值不同**（−128 vs 0）：前者下界钳位 = ReLU，后者 = 纯饱和；公式形状完全相同 |

### 8.2 第一轮暴露的薄弱点（已修正）

> **核心问题：没有把 `zero_point` 当作"坐标系的平移量"来理解。**

统一心法：$x = S\,(q - z)$，**`z` 定义的是"哪个整数代表实数 0"**。

| `z` | 含义 | 本模型出现在 |
|---|---|---|
| 0 | 整数 0 就是实数 0 | 输入 `s`、输出 `y`（∈ [−1,1] 对称） |
| −128 | 整数 −128 才是实数 0 | 隐藏层（ReLU 之后非负） |

用这一条，"ReLU 藏在哪一行"（第 4 题）和"输出层差在哪"（第 5 题）**是同一件事**。

**另一个修正点**：曾把 int8 的边界记成 `0 / 255` —— 那是 **quint8 无符号**（fbgemm `.pt` 的风格）；
本项目用的 QDQ ONNX 是 **int8 有符号 `[−128, 127]`**。见 §1.1 对照表。
