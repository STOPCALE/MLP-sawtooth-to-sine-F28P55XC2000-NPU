## 1. 四个移植决策（PC → MCU）

| # | 项 | PC 版 | **MCU 版** | 理由 |
|---|---|---|---|---|
| 1 | 重量化乘子 `M` | `double` + `prepare()` 运行时算 | **编译期算好放 FLASH**（`Lx_M[]`，`float`） | 运行时零初始化、零除法 |
| 2 | 舍入魔数 | `1.5*2^52 = 6755399441055744.0` | **`1.5*2^23 = 12582912.0f`** | float 尾数只有 23 位；且**必须全程 float**（写成 double 会退化成软件模拟） |
| 3 | 浮点精度 | `double` | **`float`** | C2000 的 FPU 是**单精度 32 位**；`double` 是软件模拟，慢 10~50× |
| 4 | 结果输出 | `printf` | **`volatile` 全局变量** + 串口帧 | 板端无控制台（CCS 的 printf 走 CIO，脱离调试器不工作） |

**决策 3 的账**（这是移植里最大的一笔）：

| | 每样本浮点运算 | 单次开销 | 合计 @150 MHz |
|---|---|---|---|
| `double`（软件模拟） | 192 次 | ~75 周期 | **~96 µs** ← 占 NPU 单次(637 µs)的 15% |
| `float`（硬件 FPU） | 192 次 | ~4 周期 | **~5 µs** |

**代价**：`float` 只有 ~7 位有效数字，与 PC 的 double 版**理论上**会有 ±1 的 int8 差异。
**实测（`predict_mcu_f32.py`，1000 点）**：

```
q1: 0/64000 不同    q2: 0/64000 不同    y: 0/1000 不同
max |prod_f32 - prod_f64|   = 3.03e-05     <- 扰动
min distance to .5 boundary = 5.22e-05     <- 余量
headroom / perturbation     = 2x           <- 只赢 2 倍
```

> **结论**：float32 可行，但**只赢 2 倍余量**——是"刚好够用"，不是"设计上安全"。
> 真要稳，应上 **int32 定点乘子** $M_0\cdot2^{-shift}$（完全精确、更快、避开浮点）。

## 2. 🔴 最大的坑：**C28x 没有 8 位类型**

```
quant_params_mcu.h, line 17: error #20: identifier "int8_t" is undefined
```

**C28x 的 `char` 是 16 位**，ISA 里没有 8 位标量 → TI 的 `stdint.h` **不提供 `int8_t`**。

**解法**：用 **`int16_t` 当容器**存 int8 范围的值（−128…127）。

| | PC 版 | MCU 版 |
|---|---|---|
| 容器 | `int8_t` | **`int16_t`** |
| 存的值 | −128…127 | **同样的 −128…127** |
| 数据量 | 4224 B | 8448 B（FLASH 544 KB，无压力） |
| 数值语义 | — | **完全不变**（已用 PC 预演验证：maxerr 3.135702e-2 前后一字不差） |

> 副产品：16 位容器不会在 128 处 wrap，所以 `s=1.0` 的绕圈隐患**天然消失**（但仍保留 clip，因为那是 ONNX 的语义）。

## 3. 🔴 构建系统：三层，都要登记

| 层 | 文件 | 管什么 | 改动 |
|---|---|---|---|
| **源头** | `.cproject` | 工程属性（优化等级等 4 个配置） | `OPT_LEVEL.off` → `OPT_LEVEL.2` |
| **汇编车间** | `CPU1_FLASH/subdir_vars.mk` | **编译哪些 .c** | `C_SRCS` / `C_DEPS` / `OBJS` 各加一行 |
| **总装车间** | `CPU1_FLASH/makefile` | **链接哪些 .obj** | `ORDERED_OBJS` 加 `"./hand_infer.obj"` |
| （编译规则） | `subdir_rules.mk` ×2 | 每条编译命令的参数 | `-Ooff` → `-O2` |

**典型症状对照**：

| 症状 | 缺了哪一层 |
|---|---|
| `undefined symbol: hand_selftest` | `makefile` 的 `ORDERED_OBJS` 没登记（编译过了但没链接） |
| 编译日志里没有 `hand_infer.c` | `subdir_vars.mk` 的 `C_SRCS` 没登记 |
| `missing separator`，报错行号指向**下一行** | 上一行**漏了续行符 ` \`** |

**续行规则**：
```makefile
A += \
x \
y \
z          ← 最后一行不要 \

```

> ⚠️ 这些文件都是 `"Automatically-generated file. Do not edit!"`。
> **在 CCS GUI 里改工程属性并 Build，会重新生成并覆盖全部手改。**
> 顺序：**先改 `.cproject`（源头），再补 makefile 的手工登记**；反过来会被吃掉。
> 重建后要重做的三件事：① `subdir_vars.mk` 加 `hand_infer.c/.d/.obj`；② `makefile` 加 `"./hand_infer.obj"`；③ 确认 `../artifacts/mod.a` 还在。

## 4. 优化等级：为什么改了 `.cproject` 还不生效

`-Ooff` 一共藏在 **5 处**：

| 文件 | 处数 |
|---|---|
| `CPU1_FLASH/subdir_rules.mk` | 2 |
| `CPU1_FLASH/device/subdir_rules.mk` | 2 |
| `CPU1_FLASH/makefile` | 1 |

**原因**：构建是用 **VS Code 任务直接调 `gmake`**，这条路径**不触发 CCS 的工程重生成**，
所以只改 `.cproject` 不影响已生成的 `makefile` / `subdir_rules.mk`。

**为什么必须改**：`-Ooff` 下 `hand_infer.c` 是**未优化代码**，而对比对象 `mod.a` 是**已优化的预编译库**
——不对等的比较会严重低估 CPU。

**改后的风险**：`-O2` 给了编译器优化浮点的机会，**可能把魔数技巧 `(x+MAGIC)-MAGIC` 折叠掉**。
→ 靠板端 `g_st_maxerr` 自检来抓（见 §5）。

## 5. 上板前先"预演"：PC 上跑 MCU 的代码

`test_hand_infer.c`（脚手架工具）：用**主机 gcc** 编译 `hand_infer.c`，直接跑它的自检。

```
hand_selftest: maxerr = 3.135702e-002  at s = -1.0000
expected     : maxerr ~ 3.14e-2        (PC PTQ 实测 3.136e-2)
```

**这就是上板判据的来源**——上板前就知道"应该看到什么数"。

**顺带验了魔数没被折叠**（看汇编）：
```asm
addss   %xmm1, %xmm0      ; x + 1.5*2^23
subss   %xmm1, %xmm0      ; - 1.5*2^23
cvttss2si  %xmm0, %eax    ; (int32_t)
```

### 板端判读表

| `g_st_maxerr` | 结论 |
|---|---|
| **≈ 3.1e-2** | ✅ 移植正确，`-O2` 没破坏魔数 |
| **0.1 ~ 1.0** | ❌ 魔数被折叠 → 加 `volatile` 或降优化等级 |
| **= −1.0（没变）** | ❌ 自检没执行 |
| 其他怪值 | ❌ 另有 bug |

## 6. 🔴 速率对比的"单位陷阱"

| | 一次推理处理几个点 |
|---|---|
| **NPU**（`tvmgen_default_run`） | **10 个点**（窗口 `(1,1,10,1)`） |
| **手写 CPU**（`hand_infer_one`） | **1 个点** |

**直接比 `g_us_last` 和 `g_us_cpu` 是错的**（差 10 倍单位）：

$$\text{NPU 每点}=\frac{g\_us\_last}{10},\qquad \text{CPU 每点}=g\_us\_cpu$$

> 而且**小模型上 NPU 未必赢**——637.6 µs 对 4224 个 MAC 来说，固定调度/搬运开销占比很高。
